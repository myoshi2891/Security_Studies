      第2章 Secure SDLC（安全な開発ライフサイクル）

      2.1 Secure SDLC とは

      SDLC（Software Development Life Cycle）は「要件 → 設計 → 実装 → テスト → リリース → 運用」という開発の流れです。Secure SDLC は、その各段階にセキュリティ活動を組み込むことです。「最後にペンテストをして終わり」ではなく、早い段階（Shift Left）から継続的に行います。

      2.2 全体フロー（セキュリティゲート付き）

      2.3 参考にする"公式の型": NIST SSDF

      SSDF（Secure Software Development Framework, NIST SP 800-218） は、安全な開発の実践を4つのグループに整理した枠組みです。

      グループ略称中身（やさしい言い換え）
      Prepare the OrganizationPO方針・役割・ツール・教育を整える
      Protect the SoftwarePSソースコード・成果物を改ざんから守る
      Produce Well-Secured SoftwarePW設計・実装・レビュー・テストで安全に作る
      Respond to VulnerabilitiesRV脆弱性を見つけて直し、根本原因まで分析する

      2026年11月時点の更新状況

      項目状況（調査時点）
      SSDF 1.1（SP 800-218）2022-02 に最終版
      SSDF 1.2（SP 800-218 Rev.1）2025-12-17 に初版ドラフト公開、コメント受付は 2026-01-30 に終了。ドラフトでは PO.6 継続的改善、PS.4 堅牢で信頼できる更新、AI がコードを生成する場合への言及などが追加。NIST の公式一覧ページ（更新日 2026-04-13）では私が確認した時点で Draft 表記。最終版の有無は NIST 公式で要確認
      SP 800-218A生成AI・デュアルユース基盤モデル向けの SSDF コミュニティプロファイル（2024-07-26 最終）

      2.4 ステップバイステップ: 各フェーズでやること

      Step 1: 要件定義 —「何を守るか」を言葉にする

      やること具体例成果物
      守る資産を洗い出す個人情報、決済情報、APIキー、ソースコード資産一覧
      セキュリティ要件を書く「管理画面は多要素認証必須」「ログは 1 年保存」要件定義書の非機能要件
      規制・契約を確認する個人情報保護法、PCI DSS、EU CRA（第5章参照）コンプライアンス表
      検証基準を決めるOWASP ASVS のレベル（L1/L2/L3）を選ぶ目標レベルの合意
      補足

      ASVS（Application Security Verification Standard） は"Webアプリが満たすべきセキュリティ要件のチェックリスト"です。「何をもって安全とするか」を決める物差しになります。

      Step 2: 設計 — 脅威モデリングで"壊れ方"を先に考える

      脅威モデリングは、コードを書く前に「どう攻撃されるか」を考える作業です。Adam Shostack が広めた4つの問いが定番です。

      STRIDE 早見表（初学者はまずこれだけ）

      頭文字脅威一言で典型的な対策
      Sなりすまし（Spoofing）他人のふりをする強い認証（パスキー、MFA）
      T改ざん（Tampering）データを書き換える署名、整合性チェック、入力検証
      R否認（Repudiation）「やっていない」と言える監査ログ、改ざん検知
      I情報漏えい（Information disclosure）見せてはいけないものが見える暗号化、アクセス制御
      Dサービス拒否（Denial of service）使えなくするレート制限、タイムアウト
      E権限昇格（Elevation of privilege）本来できないことができる最小権限、認可の一元化

      AI 機能を含む設計では、データフロー図に「LLM」「ツール」「ベクトルDB」「外部コンテンツ」を必ず描き込み、どこに"信頼できない文章"が入ってくるかを線で示します（第4章）。

      Step 3: 実装 — 安全なコーディングの基本ルール

      ルール理由関連（第3章）
      入力は検証し、出力は文脈に合わせてエスケープインジェクション/XSS の根本対策A05
      SQL は必ずパラメータ化クエリ文字列連結が SQL インジェクションの原因A05
      認可チェックはサーバー側で、リソース単位で行うクライアントの制御は回避できるA01
      秘密情報（鍵・トークン）をコードに書かないリポジトリ流出で即漏えいA02/A04
      エラー時は拒否（Fail Closed）し、内部情報は返さない例外処理の不備が悪用されるA10
      暗号は実績ある標準ライブラリを使う（自作しない）実装ミスが最大のリスクA04/第6章
      AI が書いたコードも人間が理解してからマージ第4章参照全般

      Step 4: ビルド/CI — 自動チェックの"安全網"

      ツール分類何を見つける例（製品名は一例）いつ動かす
      SASTソースコードの脆弱なパターンCodeQL、Semgrep などプルリクエストごと
      SCA依存ライブラリの既知脆弱性・ライセンスDependabot、OSV-Scanner などPR ごと＋毎日
      シークレットスキャンコミットされた鍵・トークンgitleaks、GitHub secret scanning などコミット前＋PR
      IaC スキャンTerraform/K8s の設定ミスCheckov、Trivy などPR ごと
      コンテナスキャンベースイメージの脆弱性Trivy、Grype などビルドごと
      補足

      注意: ツールは"導入して終わり"ではなく、誤検知の整理（トリアージ）とSLA（例: 重大は7日以内に修正）まで決めて初めて機能します。

      Step 5: テスト — 「攻撃者として」確認する

      テスト目的初学者へのヒント
      認可テスト他人のデータにアクセスできないかユーザーAのトークンでユーザーBのIDを指定してみる
      DAST動いているアプリへの疑似攻撃ステージング環境で実行
      ファジング想定外入力でクラッシュしないかパーサー・デコーダに有効
      異常系テストタイムアウト・不正データ・巨大入力A10（例外処理）対策に直結

      Step 6: リリース — 「これは正規の成果物」と証明できる状態にする

      項目内容詳細
      署名成果物（コンテナ、パッケージ）に署名第5章

      Step 7: 運用 — 見つけて、直して、学ぶ

      第3章 OWASP Top 10:2025 完全理解

      3.1 OWASP Top 10 とは

      OWASP（Open Worldwide Application Security Project）が公表する、Webアプリで特に重大なリスクのランキングです。「全部を暗記する」のではなく、開発者の共通言語として使います。2025年版は、データと業界アンケートに基づき更新され、新カテゴリが2つ加わりました。

      3.2 2025年版の一覧と変化

      順位カテゴリ2021年版からの変化一言で
      A01Broken Access Control（アクセス制御の不備）1位継続。SSRF は A01 に統合見てはいけない/操作してはいけないものに触れる
      A02Security Misconfiguration（設定ミス）5位 → 2位に上昇初期設定・過剰な公開・不要機能の有効化
      A03Software Supply Chain Failures（サプライチェーンの失敗）新規（旧「脆弱で古いコンポーネント」を拡張）依存・ビルド・配布の信頼が壊れる
      A04Cryptographic Failures（暗号の失敗）2位 → 4位暗号化しない/弱い暗号/鍵管理の不備
      A05Injection（インジェクション）3位 → 5位入力が命令として実行される
      A06Insecure Design（安全でない設計）4位 → 6位設計段階の欠陥
      A07Authentication Failures（認証の失敗）名称変更（旧: Identification and Authentication Failures）ログイン・セッション管理の不備
      A08Software or Data Integrity Failures（ソフトウェア/データの完全性の失敗）8位継続署名なし更新・信頼できないデシリアライズ
      A09Security Logging and Alerting Failures（ログとアラートの失敗）名称変更（"Monitoring"→"Alerting"）記録しても通知しなければ気づけない
      A10Mishandling of Exceptional Conditions（例外状況の不適切な処理）新規エラー・タイムアウト時に"危険な側"へ倒れる
      ソース

      出典: OWASP 公式 Top 10:2025、および複数の解説記事（第8章に URL）。

      3.3 カテゴリ別: 初学者向け解説と対策

      A01: Broken Access Control（アクセス制御の不備）

      例え話: ホテルのカードキーで、自分の部屋以外のドアも開いてしまう状態。

      よくある失敗: URL の ID を書き換えると他人の注文が見える（IDOR）。管理者用 API が一般ユーザーにも使える。

      // ❌ 悪い例: ログインしているかしか見ていない
app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  res.json(order); // 他人の注文でも返してしまう
});

// ✅ 良い例: 「このユーザーのものか」を必ず検証（サーバー側・リソース単位）
app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findOne({
    id: req.params.id,
    ownerId: req.user.id, // 所有者条件をクエリに含める
  });
  if (!order) return res.status(404).end(); // 存在有無も漏らさない
  res.json(order);
});

      対策チェック: 既定は拒否（Deny by default）／認可ロジックを一元化／所有者チェックをクエリ条件に含める／SSRF 対策（サーバーが取得してよい宛先を許可リストで制限し、内部アドレス・メタデータサービスへのアクセスを遮断）。

      A02: Security Misconfiguration（設定ミス）

      例え話: 金庫を買ったのに、初期暗証番号「0000」のまま使う。

      よくあるミス対策
      クラウドストレージの公開設定既定で非公開、IaC スキャンで検知
      デバッグ画面・スタックトレースの本番露出本番ではデバッグ無効、汎用エラー表示
      不要なポート/サービス/サンプルアプリ最小構成のイメージ、ハードニング
      セキュリティヘッダ未設定CSP、HSTS、X-Content-Type-Options などを設定

      A03: Software Supply Chain Failures（サプライチェーンの失敗）★新規

      例え話: 食材（ライブラリ）・調理場（CI）・配送（レジストリ）のどこかに毒を混ぜられる。

      A04: Cryptographic Failures（暗号の失敗）

      よくある失敗正しい方向
      平文で保存/送信TLS を使用、機密データは保存時にも暗号化

      A05: Injection（インジェクション）

      # ❌ 悪い例: 文字列連結で SQL を組み立てる
cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

# ✅ 良い例: パラメータ化クエリ（値は「データ」として扱われる）
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
      • SQL だけでなく、OS コマンド、LDAP、NoSQL、テンプレート、プロンプト（第4章） にも同じ構造があります。
      • 共通の原則は「命令とデータを混ぜない」。Simon Willison は、プロンプトインジェクションを「信頼できる内容と信頼できない内容を同じ文脈に混ぜる問題」と位置づけ、SQL インジェクションにちなんで命名しています。

      A06: Insecure Design（安全でない設計）

      • 実装を完璧にしても直らない"設計の欠陥"です（例: 回数制限がないパスワード再発行、残高チェックの競合状態）。
      • 対策: 脅威モデリング（2.4 Step 2）、セキュリティ要件の事前定義、悪用ケース（アビューズケース）のテスト。

      A07: Authentication Failures（認証の失敗）

      対策理由
      パスキー（FIDO2/WebAuthn） や MFA の提供パスキーはフィッシング耐性がある。MFA 全般に同じ耐性があるわけではなく、OTP 型 MFA のコードはリアルタイムのフィッシングで盗み取られ、中継され得る
      ログイン試行のレート制限・ロックアウト総当たり・クレデンシャルスタッフィング対策
      セッション ID はログイン後に再発行、適切な有効期限セッション固定攻撃の防止
      弱い/漏えい済みパスワードの拒否推測攻撃の成功率を下げる

      A08: Software or Data Integrity Failures（完全性の失敗）

      • 署名のない更新、信頼できないデータのデシリアライズ、CI で検証なしにダウンロードして実行などが該当します。
      • A03 が"依存関係レベル"なのに対し、A08 は信頼境界でのコード/データの完全性に焦点があります。
      • 対策: 成果物の署名と検証、ハッシュ固定、安全なデシリアライズ形式（JSON 等）の使用。

      A09: Security Logging and Alerting Failures（ログとアラートの失敗）

      記録すべきイベント注意点
      ログイン成功/失敗、権限変更、認可の拒否パスワード・トークン・個人情報はログに出さない
      管理操作、重要データの参照/エクスポート改ざんされにくい場所へ転送
      異常（短時間の大量失敗など）アラートが"誰に"届き、"いつまでに"見るかを決める

      A10: Mishandling of Exceptional Conditions（例外状況の不適切な処理）★新規

      例え話: 自動ドアが故障したとき「開きっぱなし」になるか「閉まったまま」になるか。

      # ❌ 悪い例: 認可サービスの障害時に"通してしまう"（Fail Open）
def can_access(user, resource):
    try:
        return auth_service.check(user, resource)
    except Exception:
        return True  # エラー時に許可 → 危険

# ✅ 良い例: 障害時は拒否し、ログに残す（Fail Closed）
def can_access(user, resource):
    try:
        return auth_service.check(user, resource)
    except Exception as e:
        logger.error("auth check failed", exc_info=e)  # 内部情報は応答に含めない
        return False

      対策: 例外は必ず捕捉して安全側に倒す／タイムアウト・リトライ上限・リソース上限を設定／異常系テスト（第2章 Step 5）／ユーザーには汎用メッセージ、詳細はログへ。

      4.3 C. AI エージェントと「致命的三位一体（Lethal Trifecta）」

      AI エージェントは、計画を立て、ツール（メール、ファイル、Web、社内 API など）を呼び出して実際に行動するAIです。

      Simon Willison（"prompt injection" の命名者）は 2025 年 6 月 16 日に、次の 3 つが 1 つのエージェントに揃うと、攻撃者がデータを盗めると警告しました。

      #要素例
      1機密データへのアクセス社内ドキュメント、メール、非公開リポジトリ
      2信頼できないコンテンツへの露出Web ページ、受信メール、誰でも書ける Issue、PDF
      3外部への通信手段HTTP リクエスト、メール送信、リンクの描画

      なぜ"プロンプトで禁止"では防げないのか: LLM は、運用者の指示も、読み込んだ文章中の指示も、同じ一続きのトークンとして受け取ります。どの命令が正規かを確実に区別できないため、Willison は「ガードレール製品が 95% 防げる」という売り文句を、Web セキュリティでは不合格点だと批判し、3 要素の組み合わせそのものを避けることを勧めています。

      Meta の「Agents Rule of Two」（2025年10月31日公表）

      Willison の 3 要素を発展させ、Meta は [A] 信頼できない入力の処理、[B] 機密システムまたは非公開データへのアクセス、[C] 状態変更または外部通信を評価します。人間の承認なしに動くエージェントは、1 セッション内で満たしてよいのは 2 つまでとします。現在有効な権限だけでなく、蓄積したセッション履歴も含めて判定します。

      一度読んだ機密データは、読み取り権限を外してもコンテキスト内に残ります。そこに信頼できない入力と外部通信を組み合わせる前に、攻撃経路を断つ安全な遷移（例: 外部通信を無効化し、同じセッションでは再有効化しない）か、機密データや未検証の履歴を引き継がない新しいコンテキストへの切り替えが必要です。権限の切り替えだけでカウントをリセットしてはいけません。

      信頼できない入力を読み、本番システムを操作できるエージェントは [A]・[B]・[C] のすべてを満たすため、この方針では自律動作を許可しません。根拠: Meta の公式解説。

      第6章 PQC（耐量子計算機暗号）移行

      6.1 なぜ今 PQC なのか（初学者向け）

      用語意味
      量子計算機特定の計算が極端に速くなる新しい計算機
      CRQC暗号を実際に破れるほど大規模な量子計算機（Cryptographically Relevant Quantum Computer）
      Shor のアルゴリズムCRQC 上で RSA・楕円曲線暗号（ECC）を破れる方法
      HNDL（Harvest Now, Decrypt Later）今は暗号文を盗んで保存し、将来 CRQC で解読する攻撃
      PQC量子計算機でも破られにくいとされる新しい暗号（普通のコンピュータ上で動く）

      ポイント

      • 暗号化（鍵交換）は HNDL のため今すぐ対策が必要です。
      • 署名は、CRQC が現れるまで偽造できないため緊急度が一段下がると言われてきましたが、2026 年に Google は認証（署名）の移行を優先すると表明しました（鍵の盗用リスクと、長期使用される署名鍵の存在のため）。
      • 対称暗号（AES など）は大きな問題がないとされています（Filippo Valsorda は「Grover は問題にならない」と述べています）。

      項目内容

      重要な読み方: Google も Cloudflare も「2029年に CRQC が存在する」と予測しているわけではなく、「もう否定しきれないので前倒しで備える」という立場です（PQShield の解説）。自分の守るデータの寿命が長いほど、早く動くべきです。

      6.4 いま実際に広まっているもの

      • 主要ブラウザは X25519MLKEM768（X25519 と ML-KEM-768 のハイブリッド）を TLS 鍵交換の既定にしています（Chrome 131+、Firefox 132+、Edge 131+、Safari 26+ など）。
      • Cloudflare は 2026 年 4 月時点で、人間による通信の 65% が PQ 鍵交換を使っていると報告しています（記事経由）。
      • Go の crypto/tls は Go 1.24 以降、対応相手とは既定でハイブリッド鍵交換を使います（Filippo Valsorda の 2025 年講演）。
      • 署名（証明書）は未成熟: WebPKI の実運用での ML-DSA 証明書はまだ広がっていません。鍵交換が先、署名が後という順序感になっています。

      6.5 "ハイブリッド"か"純粋 PQ"か（専門家の論点）

      立場主張出典
      鍵交換はハイブリッドX25519 + ML-KEM の併用が事実上の標準。純 ML-KEM を単独で使う主張は少数複数の解説
      署名はハイブリッド不要派Filippo Valsorda は 2026 年 4 月、複合（ハイブリッド）署名は移行時間と複雑さを増やすだけだとし、ML-DSA-44 へ直接移行を主張words.filippo.io
      慎重派ML-DSA の実装は新しくバグが出やすいため、ハイブリッドが被害を限定できるという意見もpostquantum.com の整理
      補足Google の Sophie Schmieg は、署名偽造の被害は鍵失効で限定できるため、ハイブリッド署名の必要性は鍵交換より低いと IETF で述べたと紹介同上
      ベストプラクティス

      初学者向けの結論: 鍵交換は ハイブリッド（X25519+ML-KEM-768）、署名は まず標準ライブラリとプロトコルの対応状況に従う。専門家の間でも意見が割れる領域なので、自分で暗号を組み合わせないことが最優先です。

      用途推奨

      公開鍵暗号（HPKE）MLKEM768-X25519（X-Wing）+ HKDF-SHA256 + AES-128-GCM、または PQ 鍵付き age

      6.6 ステップバイステップ: PQC 移行計画の作り方

      Step 1: 暗号の棚卸し（CBOM: Cryptographic Bill of Materials）

      調べること例方法
      どこで公開鍵暗号を使っているかTLS、SSH、VPN、JWT 署名、コード署名、証明書、データベース暗号化、メールコード検索（RSA, ECDSA, secp256r1 等）、設定ファイル、証明書一覧、ネットワーク観測

      鍵の寿命10 年以上保護が必要なデータデータ分類

      Step 2: 優先順位付けの考え方

      優先度条件例
      高長期保護が必要なデータをネットワーク越しに送る（HNDL の標的）医療・研究・政府・金融の長期機密通信
      高長寿命の署名鍵や信頼の起点ルート CA、ファームウェア署名、コード署名
      中長期の機密保持を要しない Web 通信。優先度はセッションの長さやブラウザの対応だけでなく、必要な機密保持期間と実際に合意した鍵交換方式で判断ハイブリッド非対応の相手とは従来方式になる場合がある。従来方式で送る長期機密データは、短いセッションでも通信の記録・将来の復号（HNDL）の対象となるため高
      低数日で価値が失われるデータ一時的な通知

      Step 3: 暗号アジリティ（入れ替えやすい設計）

      # ❌ 悪い例: アルゴリズムをコードに直書き
signature = rsa_sign(private_key, data)

# ✅ 良い例: アルゴリズムを設定とメタデータで管理（差し替え・併用が可能）
cfg = load_crypto_policy()             # 例: {"sign": "ml-dsa-44", "kem": "x25519-mlkem768"}
signature = signer_for(cfg["sign"]).sign(private_key, data)
envelope = {"alg": cfg["sign"], "sig": signature}  # どのアルゴリズムで署名したかを必ず記録
      • 鍵・署名・証明書のサイズ増加（PQC は鍵や署名が大きい）を前提に、プロトコルの上限（パケット、フィールド長、DB カラム）を見直します。ML-KEM-768 の暗号文は 1 KB 超、SLH-DSA の署名は数十 KB になり得ます。

      Step 4: 鍵交換のハイブリッド化（先行して実施）

      対象実施内容
      TLS（Web/API）TLS ライブラリ・リバースプロキシ・CDN を、X25519MLKEM768 に対応する版へ更新。既定で有効なことが多いので、まず現状の実際のネゴシエーション結果を確認
      VPN・社内通信製品のロードマップを確認。WireGuard などプロトコルの更新が必要なものは要注意
      保存データ将来の復号に備え、長期保存データの暗号方式を見直す

      Step 5: 署名の移行計画

      • コード署名・ファームウェア・ドキュメント署名・社内 PKIを洗い出す。
      • 標準化が確定している ML-DSA（FIPS 204） を第一候補に、サイズ制約が厳しい場合は FN-DSA（FIPS 206 の確定待ち）、長期の信頼の起点では SLH-DSA（FIPS 205）。

      質問理由
