1. CSSLP とは

1.1 一言でいうと

「ソフトウェア開発ライフサイクル（SDLC）の“全フェーズ”にセキュリティを組み込む専門性」を証明する ISC2 の認定資格です。

ISC2 の公式ページでは、CSSLP は SDLC 全体にわたる 認証（Authentication）・認可（Authorization）・監査（Auditing） のベストプラクティスを適用する高度な技術力と知識を示すもの、と説明されています。

公式ページに記載のポイント 内容
必要な実務経験 4年（累積・フルタイム、8ドメインのうち1つ以上）。コンピュータサイエンス・IT など関連分野の学士号または修士号で、最大1年分を充当できる
規格適合 ANAB 認定（ISO/IEC 17024）
米国防総省 DoDM 8140.03 で承認
経験が足りない場合 試験に合格すると Associate of ISC2 になれる。その後、合格から5年以内に必要な実務経験を満たす必要がある

3.1 【1.1】コアコンセプトを理解する

Step 1: CIA トライアド＋αを押さえる

概念 一言で 実装例（公式アウトライン例示） ベストプラクティス
Confidentiality（機密性） 見てはいけない人に見せない 暗号化 通信は TLS、保管データは強力な共通鍵暗号。独自暗号は作らず、検証済みライブラリを使う。鍵管理を設計に含める
Integrity（完全性） 勝手に改ざんされない ハッシュ、デジタル署名、コード署名 改ざん検知には HMAC／デジタル署名。単なるハッシュは「改ざんした人が再計算できる」点に注意
Availability（可用性） 必要なときに使える 冗長化、レプリケーション、クラスタリング、スケーラビリティ、レジリエンス 単一障害点を排除。レート制限・リソース上限で DoS 耐性を持たせる
Authentication（認証） 本人であることの確認 MFA、IAM、SSO、フェデレーション、生体認証 MFA を標準に。認証基盤は自作せず IdP（OIDC/SAML）を活用。パスワードレス（パスキー）も検討
Authorization（認可） 何をしてよいかの制御 アクセス制御、権限、エンタイトルメント デフォルト拒否。認可チェックは必ずサーバー側で実施。リソース単位で検証
Accountability（説明責任） 誰が何をしたか追える 監査、ログ 改ざん困難なログ保管、時刻同期、ユーザー ID の紐づけ
Nonrepudiation（否認防止） 「やっていない」と言わせない デジタル署名、ブロックチェーン データの完全性と、特定の秘密鍵保有者に由来すること（起源）を、デジタル署名と署名者の公開鍵（証明書）との対応から第三者が検証できることで成立。タイムスタンプは署名時刻を示す補助的な証跡
GRC ガバナンス・リスク・コンプライアンス 規制当局、法律、業界標準 規制要件を要件定義の段階で洗い出す

Step 2: AAA の流れを図で理解する

Step 3: 混同しやすい用語を整理する

比較 違い 覚え方
認証 vs 認可 認証＝「誰か」、認可＝「何ができるか」 空港のパスポート確認と搭乗ゲートの権限
暗号化 vs ハッシュ 暗号化は元に戻せる、ハッシュは一方向 金庫（開けられる）と指紋（戻せない）
ハッシュ vs 署名 署名は誰が作ったかまで保証 ハッシュ＋秘密鍵
エンコード vs 暗号化 エンコードは形式変換で秘匿性なし（Base64 等） 暗号ではない
完全性 vs 否認防止 否認防止は行為者の特定まで必要 改ざんされていない＋誰がやったか
試験ポイント

「パスワードを DB に保存する」シナリオでは、暗号化ではなくソルト付きの遅い一方向ハッシュ（bcrypt/scrypt/Argon2 等）が正解になりやすい。

3.2 【1.2】セキュア設計原則を理解する

補足

公式が列挙する10原則。Saltzer と Schroeder の古典的な原則が土台です。「原則名 → 具体例」の対応が頻出です。

# 原則 平易な説明 アウトライン例示 ベストプラクティス
1 Least privilege（最小権限） 必要最小限の権限だけ与える アクセス制御、need-to-know、実行時権限、Zero Trust サービスアカウントは専用・最小権限。管理者権限での常時稼働を避ける。期限付き権限（JIT）
2 Segregation of Duties（職務分離） 1人に全権を持たせない 多者統制、秘密分散、知識分割 「コードを書く人」と「本番へ承認する人」を分ける。重要鍵は分割管理
3 Defense in depth（多層防御） 防御を何層も重ねる 階層化された制御、地理的・技術的多様性 入力検証＋WAF＋権限制御＋監視など、1層が破られても止まる設計
4 Resiliency（回復力） 障害時も安全・継続 fail safe、fail secure、単一障害点排除、フェイルオーバー 障害時の振る舞い（開く／閉じる）を設計時に明示
5 Economy of mechanism（機構の経済性） 仕組みはシンプルに SSO、パスワード保管庫、リソース効率 複雑さ＝バグの温床。機能と実装を最小化
6 Complete mediation（完全な仲介） 毎回アクセス権を確認 Cookie 管理、セッション管理、資格情報のキャッシュ 認可結果を長時間キャッシュしない。リクエストごとに検証
7 Open design（オープン設計） 秘密は鍵だけ、設計は公開前提 ケルクホフスの原則、ピアレビュー、OSS 「設計の秘匿」に依存しない（Security through obscurity を避ける）
8 Least common mechanism（共通機構の最小化） ユーザー間で共有する仕組みを減らす 区画化／隔離、許可リスト テナント分離、コンテナ・サンドボックスで隔離
9 Psychological acceptability（心理的受容性） 使いにくい対策は回避される パスワード複雑性、パスワードレス、画面設計、CAPTCHA セキュリティとユーザビリティの両立。過剰な定期変更強制は逆効果
10 Component reuse（コンポーネント再利用） 実績ある部品を使い回す 共通コントロール、ライブラリ 認証・暗号は検証済み共通部品を使う。ただし再利用部品の脆弱性管理も必須（→ Domain 8）

fail safe と fail secure の違い（最頻出の引っかけ）

用語 重視するもの 例
fail safe 障害時に、データ・財産・生命を含む指定された対象への損害を防ぐ 物理的な電源断時の例: 火災時に電子ロックの扉が開く（人命を守る）
fail secure 障害時に、セキュアな状態が失われることを防ぐ 物理的な電源断時の例: 停電時に金庫室の扉が閉まったまま（資産を守る）
試験ポイント

  • 「毎回確認する」→ Complete mediation
  • 「鍵以外は公開してよい」→ Open design
  • 「共有を減らす／隔離」→ Least common mechanism
  • 「使いにくいと回避される」→ Psychological acceptability
  • 「複数人の承認が必要」→ Segregation of Duties

4.2 【2.2】セキュリティ標準を特定・採用する

標準／フレームワーク 種別 何をするものか
ISO（27001／27034 等） 国際規格 情報セキュリティマネジメント、アプリケーションセキュリティ
PCI DSS 業界標準 カード情報を扱うシステムの要件
NIST（SSDF／RMF 等） 政府系ガイダンス セキュア開発の実践、リスク管理の枠組み
OWASP（Top 10／ASVS／SAMM） コミュニティ 脆弱性の認知、検証基準、成熟度モデル
SAFECode 業界団体 セキュアな開発実践のガイダンス

補足

SAMM と BSIMM の違い: SAMM は「どうあるべきか」を示す規範的モデル、BSIMM は「他社が実際にやっていること」を記述する観測的モデル、と整理すると混同しにくくなります。

ベストプラクティス

標準は「全部採用」ではなく、自社の規制・リスクに合うものを選び、ギャップ分析→ロードマップ化する。セキュリティ意識向上（awareness）の教育もセットで計画する。

指標の種類 例（アウトライン例示を含む） 見方

脅威モデリングとは

補足

コード例 1: SQL インジェクションの対策（パラメータ化クエリ）

#  危険: 入力を文字列連結して SQL を組み立てる
query = f"SELECT * FROM users WHERE email = '{email}'"
cursor.execute(query)

#  安全: プレースホルダ（パラメータ化クエリ）を使う
# %s は DB-API の format 形式を使うドライバー（例: psycopg、PyMySQL）向け。
# プレースホルダ形式はドライバー固有で、sqlite3 では ? または :email のような名前付き形式を使う。
query = "SELECT * FROM users WHERE email = %s"
cursor.execute(query, (email,))

なぜ安全か: 入力値がSQL の構文ではなく「データ」として扱われるため、攻撃文字列がクエリの構造を変えられません。

コード例 2: 出力エンコーディング（XSS 対策）

import html

user_input = '<script>alert(1)</script>'

#  危険: そのまま HTML に埋め込む
page = f"<p>{user_input}</p>"

#  安全: HTML コンテキスト用にエスケープして出力
page = f"<p>{html.escape(user_input)}</p>"
補足

重要: エンコードは出力先（HTML 本文／属性／JavaScript／URL）ごとに方法が異なるため、テンプレートエンジンの自動エスケープ機能を既定で有効にするのが基本です。

コード例 3: 安全なエラー処理（情報を出しすぎない）

import logging
import uuid

logger = logging.getLogger(__name__)

def handle_request():
    try:
        process()
    except Exception as exc:
        # 例外メッセージやスタックトレースには機密値が混入しうるため出力しない。
        # 調査用に相関できるエラーIDと、例外の型名（サニタイズ済み情報）だけを記録する
        error_id = uuid.uuid4().hex
        logger.error("request processing failed error_id=%s type=%s", error_id, type(exc).__name__)
        # 利用者には汎用メッセージと問い合わせ用のエラーIDのみ返す（fail secure）
        return {"error": "処理に失敗しました", "error_id": error_id}, 500
