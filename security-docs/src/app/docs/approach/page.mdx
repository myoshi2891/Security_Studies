  <DocsSubheading color="red">1. Axios NPM パッケージ侵害 (CVE-2026-33634)</DocsSubheading>
  
  リードメンテナーのアカウントが乗っ取られ、GitHub上のソースには現れない「幻の依存関係（Phantom Dependency）」をnpmレジトリ上で直接挿入された事件です。

      },
      {
        title: "ポストインストールスクリプトの起動",
        content: "開発者やCI/CDシステムが `npm install` を実行した際、自動的に `plain-crypto-js` がダウンロードされ、その中の `postinstall` フックにより難読化された `setup.js` が自動起動。"
      },
      {

      },
      {

        content: "実行完了後、`setup.js` は自身を削除し、悪意ある記述のある `package.json` を削除。事前に用意されていた安全なスタブファイル `package.md` を `package.json` に上書きして証拠隠滅。"
      }
    ]}
  />

  **原因と問題点:**
  - GitHub上のソースコードとnpmレジトリ上のバイナリ（tarball）との間で完全性検証が行われておらず、レジストリ直書きの侵害を検知できなかったこと。
  - パッケージインストール時にデフォルトで任意のシステムコードが実行可能なライフサイクルスクリプト（`postinstall`）仕様の盲点。

  **解決策ベストプラクティス:**
  - `npm install --ignore-scripts` を徹底するか、`.npmrc` に `ignore-scripts=true` を記述してライフサイクルスクリプトの自動実行を恒久的に防ぐ。
  - `overrides`（npm）または `resolutions`（yarn/pnpm）を `package.json` に指定し、間接的に呼び出されるAxiosのバージョンを安全なもの（v1.14.0 または v0.30.3）に強制固定する。

  **原因と問題点:**
  - `pull_request_target` を無制限に信頼し、フォーク元のPRからシークレットやキャッシュ領域へのアクセスを許したこと。

  - **重要:** 侵害された可能性のあるトークンを無効化する前に、**必ず**ローカルシステム上の永続化デーモン（Linux：`kitty-monitor.service`、macOS：`com.user.kitty-monitor.plist`）およびAIツールの設定フック（`.claude/settings.json`）を物理削除すること。
  - GitHub ActionsにおけるOIDC信頼条件（Trust Conditions）で、特定のメインブランチやタグ、セキュアなランナーのみに署名権限を与えるポリシーを構成する。

  **不正アクセスプロセスと根本原因:**
  1. **Free-For-Teacher 制度の脆弱性：** Canvasが提供していた「教師向け無料アカウント」プログラムの認証ロジック、あるいはプロビジョニング設定の不備を突いて初期アクセスを確立。
  2. **バックエンドへの権限昇格：** 攻撃者は初期のアクセス権を踏み台とし、特権APIクレデンシャルや認証トークンを複製・改ざんすることで、Canvasのクラウドバックエンドシステム全体に対する管理者特権を獲得。
  3. **データ流出：** プライベートメッセージ、相談内容、個別の配慮要求を含む機微データベースをバルク抽出。
  4. **改ざんと恐喝：** ShinyHuntersがLMSログイン画面を改ざん（Deface）し、身代金の支払いを要求。システムは完全オフラインに追い込まれた。

  <Callout type="warning" title="潜在的リスク：文脈依存型（コンテキストアウェア）スピアフィッシング">
    攻撃者は、学生の実名、正確な大学ドメインのメールアドレス、現在受講している授業の具体的なクラス名、教官名、さらに「過去に教官と交わした未公開のやり取りメッセージ」をすべて把握しています。これにより、以下のような、防御が困難なフィッシングが作成可能になりました。
    
    *「○○教授による『後期微分積分学』を受講中、病気療養のための相談をされていた学生（ID: 12345）の方へ。提出期限が切迫しているため、本メールに添付された追加申請フォーム（実際にはマルウェア）を至急確認してください。」*
    
    この具体的なコンテキストを含んだフィッシングは、セキュリティ意識の高い学生であっても騙されやすく、さらなるマルウェア感染を招く引き金となります。
  </Callout>
</SectionCard>

<SectionCard eyebrow="Section 04" title="プロセスの完全性証明と自動化技術（SBOM / SLSA / Cosign / VEX）">
  「何が入っているか（SBOM）」「正しく作られたか（SLSA）」「改ざんされていないか（Cosign）」「悪用可能か（VEX）」を自動で検証する技術的対策が、現代のデファクトスタンダードとなっています。

  <h3 className="text-lg font-bold mt-6 mb-2">1. SBOM（ソフトウェア部品表）の義務化と現実</h3>
  - CycloneDX（OWASP推奨、セキュリティ用途に最適化）やSPDX（Linux Foundation、ライセンスに強み）が標準規格。
  - **2026年の現実:** DigiCertの2026年調査によると、完全なSBOMを動的に提供できている組織は**わずか11%**。法的義務と実践の乖離が大きいため、早期のCI/CD統合が必要です。

  <Terminal title="SBOMの生成と検証手順">
    {`# Node.js プロジェクトのSBOM生成
npx @cyclonedx/cyclonedx-npm --output-format JSON --output-file sbom.json

# コンテナイメージのSBOM生成
trivy image --format cyclonedx --output sbom-image.json myapp:v1.0.0

# SBOMを用いて既知CVEをスキャン
grype sbom:./sbom.json --fail-on high`}
  </Terminal>

  <h3 className="text-lg font-bold mt-8 mb-2">2. SLSA（サルサ）とCosign</h3>
  - **SLSA (Supply-chain Levels for Software Artifacts):** ビルドプロセスの完全性を暗号学的に証明する4段階のフレームワーク。ビルドの「来歴（Provenance）」を生成。
  - **Cosign:** コンテナイメージやSBOMに暗号署名を付与し、改ざんを検知するツール。キーレス署名（OIDC）が主力。

  <Terminal title="来歴検証とCosign署名の検証">
    {`# SLSA来歴の検証
slsa-verifier verify-image "myapp:v1.2.0" \\
  --provenance-path provenance.json \\
  --source-uri github.com/my-org/my-repo \\
  --source-tag v1.2.0

# Cosignによるキーレス署名検証
cosign verify \\
  --certificate-identity="https://github.com/my-org/my-repo/.github/workflows/build.yml@refs/heads/main" \\
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com" \\
  ghcr.io/my-org/my-app:v1.0.0`}
  </Terminal>

  <h3 className="text-lg font-bold mt-8 mb-2">3. VEX（脆弱性悪用可能性交換）によるノイズ削減</h3>
  SCAツールによるCVEの大量検出ノイズに対し、製品のコンテキストで「悪用可能か」を機械可読な形式で宣言します。

  <DataTable
    headers={["VEX ステータス", "意味", "対応"]}
    rows={[
      ["affected", "実際に悪用可能", "即座にパッチ適用"],
      ["not_affected", "悪用不可能", "対象機能を未使用・無効化済み（調査不要へ）"],
      ["fixed", "修正済み", "対応不要"],
      ["under_investigation", "調査中", "48〜72時間以内に更新"]
    ]}
  />

  <h3 className="text-lg font-bold mt-8 mb-2">4. PQC（耐量子計算機暗号）の影響と対応</h3>
  「Harvest now, decrypt later（今収集し、後で解読する）」攻撃に備え、暗号インベントリ（CBOM）を作成し、ML-DSAやML-KEMといった耐量子アルゴリズムへの移行（クリプトアジリティの確保）を進める必要があります。
</SectionCard>

  ### 2. 達成すべき2大実務要件と実装ステップ

  #### ① 【教育の義務化要件：4-2-1-2】（★3 / ★4 必須）
  - **目的:** 組織内の全要員に対して、最新のサイバー攻撃手法（ソーシャルエンジニアリング、AIインジェクション等）への理解を高め、ヒューマンエラーを防ぐ。
  - **対象:** 経営陣、一般正社員、契約社員、派遣社員、受入出向者すべて。
  - **頻度:** 年1回以上。
  - **実施ステップ:**
    1. **カリキュラム策定:** 最新の「AI設定ファイル汚染」や「LMS偽画面デフェース」などの脅威トレンドを教材に反映。
    2. **受講管理:** eラーニングシステム等を用い、受講率 100% を目指して実行。
    3. **エビデンス保管:** 監査に備え、研修実施記録、テスト結果、受講署名リストを保管。

  #### ② 【子会社・取引先の確認要件：2-1-3-1】（★4 必須）
  - **目的:** セキュリティ水準の低い関連会社や委託先を「踏み台」とした、自社への侵害を未然に防止する。
  - **対象:** 機密情報を共有している取引先、ビジネス継続性に影響を及ぼすサービス供給者、VPN等で自社ネットワークへ接続可能な取引先。
  - **頻度:** 年1回以上。
  - **実施ステップ:**
    1. **Tier分け:** 依存している関係先をリストアップし、リスク影響度に応じて分類。
    2. **アセスメント:** SCS基準やISMAP、SOC2レポートを活用し、対策レベル（★3相当以上か）を評価。
    3. **是正フォロー:** 不備が見つかった場合、改善計画の提出を求め、従わない場合はネットワークアクセス制限や取引量見直しを実施。
